# /improve — 분석 → 선택 → 실행 사이클

이 프로젝트에서 가장 자주 반복되는 워크플로우. 사용자는 항상
**(1) 관점별 분석 보고 → (2) 번호로 선택 → (3) 선택분만 일괄 실행·검증·푸시** 순서로 일한다.
분석 단계에서 절대 코드를 고치지 말 것 — 보고가 결과물이다.

## 트리거
- "개선할 거 분석해줘", "UI/UX 관점으로 제안해줘", "버전업 관점이야"
- 분석 후 "1번, 3번 진행", "1차만 진행", "추천한 순서대로 가자"

## 입력
- 분석 관점(사용자 지정, 없으면 기본 3종: UI/UX · 자료사용 · 제거/정리)
- 실행 단계에서: 선택된 번호 목록

## 단계
### A. 분석 모드 (실행 요청이 아직 없을 때)
1. 코드베이스를 실제로 훑어 근거를 수집한다 (추측 금지 — 파일:라인 근거).
2. 관점별로 항목화하고 **각 항목에 고유 번호**를 붙인다 (예: A1, B4). 사용자가 번호로 답하기 때문.
3. 항목마다: 한 줄 문제 진단 + 한 줄 제안 + 체감 효과. 표보다 짧은 문단.
4. 마지막에 **추천 실행 순서**(묶음 단위)를 제시한다. 서로 재료를 공유하는 항목은 같은 묶음으로.
5. 여기서 멈춘다. 코드 수정 없음.

### B. 실행 모드 (번호/묶음이 선택되면)
1. 선택된 항목만 구현한다. 범위 확장 금지.
2. 항목 간 공유 데이터/컴포넌트를 먼저 만들고 재사용한다.
3. 검증 체인 통과: `npx tsc --noEmit` → 변경 파일만 `npx eslint` → `npm run build` → `npx vitest run`.
4. /ship 절차로 커밋·푸시 (커밋 메시지에 항목 번호 명시).
5. 보고: 항목별 "무엇이 어떻게 바뀌었나" + 배포 후 확인 포인트 + 사용자가 해야 할 수동 조치(SQL 적용 등).

## 출력
- 분석 모드: 번호 매긴 관점별 제안 + 추천 순서 (코드 변경 0)
- 실행 모드: 커밋 해시 + 항목별 변경 요약 + 수동 조치 목록

## 주의
- 기존 항목 번호를 대화 중간에 바꾸지 말 것 (사용자가 이전 번호로 지시함).
- 수동 조치(Supabase SQL, 로컬 스크립트, Vercel 환경변수)는 HANDOVER.md §11에 누적 기록.
