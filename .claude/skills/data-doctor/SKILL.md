# /data-doctor — 데이터 수집·적재 디버그 루프

실사례: 행정동 인구 API가 "정상"인데 0건 — 원인은 3중(만료된 uddi + returnType 파라미터 + 필드명 불일치)이었고,
로컬 실행↔출력 붙여넣기 왕복 4회로 해결했다. 이 왕복을 최소화하는 프로토콜.

## 트리거
- "API가 0건이야", "키 넣었어 확인해줘", 수집 스크립트 실패 출력 붙여넣기, 업로드 데이터 이상

## 환경 제약 (먼저 판단)
- **원격 환경에서 불가**: Kakao·odcloud·data.go.kr 등 외부 API 직접 호출(프록시 403), 보안 엑셀 열기, .env.local 접근.
  → 이 경우 즉시 "로컬 실행 프로토콜"로 전환. 원격에서 재시도 반복하지 말 것.
- **원격에서 가능**: 코드 수정, 스크립트 로직 검토, Supabase(MCP/서비스롤) 조회, 저장된 JSON 검증.

## 로컬 실행 프로토콜
1. 사용자에게 **정확한 명령 한 줄**을 준다: `node scripts/xxx.mjs` (+필요 env 키 이름, 값은 묻지 않음).
2. **진단 출력을 먼저 심는다**: 스크립트가 실패 지점에서 요청 URL(키 마스킹)·응답 원문 일부·행 수를 찍도록
   수정한 뒤 실행을 요청한다. "그냥 다시 돌려보세요"는 금지 — 왕복 1회가 비싸다.
3. 사용자가 붙여넣은 출력에서 판정한다. 흔한 원인 순서:
   - **odcloud/공공데이터포털**: uddi가 월마다 바뀜(포털에서 최신 확인) / Encoding vs Decoding 키 혼용 /
     `returnType=JSON` 넣으면 빈 응답 / perPage 과대(1000 이하로) / 필드명 실제 응답과 대조("0세남자" vs "만0세남자").
   - **Kakao**: KAKAO_REST_API_KEY 미설정, 쿼터, 주소 자체가 동-단위로 부정확.
   - **Supabase 적재**: RLS 차단(정책 role 확인), 1000행 기본 제한(range 페이징), bigint에 소수.
4. 수정 → 다시 한 줄 명령 → 반복. **키 값이 채팅에 노출되면 즉시 재발급을 권고**한다.
5. 성공하면: 생성/갱신된 데이터 파일을 커밋 대상으로 안내하고, 스크립트 헤더의 갱신일 주석을 업데이트.

## 출력
- 각 왕복마다: 판정(원인) + 수정 내용 + 다음에 돌릴 명령 한 줄
- 종료 시: 무엇이 갱신됐고 어디에 커밋해야 하는지

## 참고
- 수집 자동화: `.github/workflows/data-refresh.yml` (시크릿 KAKAO_REST_API_KEY / DATA_GO_KR_POP_KEY / SBIZ_API_KEY).
- 스크립트 인벤토리와 용도는 `scripts/` 헤더 주석 + HANDOVER.md 참조.
