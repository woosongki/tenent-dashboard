# /verify-metric — 대시보드 수치 역추적 검증

실사례: 당월 일평당매출이 ERP의 30일 고정 분모 때문에 7일차 파일에서 4.3배 과소 표시됐고,
사용자가 손으로 잡아냈다. 이 스킬은 그 검증을 체계화한다. **핵심은 코드를 믿지 말고
실제 숫자 하나로 손계산과 대조하는 것.**

## 트리거
- "X의 로직 알려줘", "이 숫자 맞아?", "왜 이 값이 나와?", 사용자가 구체적 수치 예시를 제시할 때

## 입력
- 화면 위치(페이지/카드/컬럼) 또는 지표 이름
- 가능하면 사용자가 본 실제 값 1개 (점포·브랜드·기간 포함)

## 단계
1. **표시 지점 → 필드 추적**: 해당 UI 컴포넌트에서 렌더링되는 필드명을 찾는다 (예: `dppSales`).
2. **산식 역추적**: 필드가 계산되는 곳까지 따라간다 (`src/lib/sales/queries.ts` 등).
   각 항의 **출처와 단위**를 명시: DB 컬럼인지, ERP 시트에서 파싱된 값인지(area_raw=평, days="N일누적"),
   상수인지(cumDays, 캘린더 말일 fallback), 조회 시 정규화되는지(area_raw×days=평·일).
3. **암묵 가정 나열**: 분모의 일수 가정, 기준월, 제외 규칙(그외 브랜드 isOthersBrand), 반올림 시점.
4. **손계산 대조**: 사용자가 준 실제 값으로 산식을 손으로 계산해 화면 값과 맞는지 확인.
   안 맞으면 어떤 가정이 깨졌는지 역산으로 특정한다 (예: 46,097 × 30/7 ≈ 사용자 기대값 → 30일 가정이 범인).
5. **판정 보고**: ①산식 ②각 항의 출처 ③깨진 가정 ④영향 범위(이 점포만? 전체?) ⑤수정 방향.
   **사용자가 고치라고 하기 전에는 보고만** — 진단이 결과물.

## 출력
- 산식 1줄 + 항별 출처 표 + 손계산 대조 결과 + (불일치 시) 원인·영향범위·수정안

## 이 프로젝트의 알려진 함정
- 당월: 저장 `area_raw`=평(면적), 조회 시 행별 `days`("N일누적" 파싱, 없으면 말일)를 곱해 평·일 정규화. 누적: ERP가 평·일로 내려줌.
- 당월 파일이 "월 중간 일자 누적"일 수 있음 → 파일에 "N일누적" 표기가 있는지, 전년/당년 평당 시트 단위가 같은지 확인(다르면 일평당 성장율이 그 배율로 튐).
- '그외' 브랜드(엠페스트·문화센터·소극장( 등)는 본 수치에서 제외되고 others로 분리됨.
- 비중(%)은 반올림(round1)이 항목별로 먼저 적용됨 — 합이 100이 안 될 수 있음.
- 상권분석 카테고리 비중은 BRANCH_CATEGORY_SOURCE에 따라 정적(2026-04) 또는 Supabase 파생.
